# PJ000001 - minmax-fx-eval-framework プロジェクト方針

> 担当: 司令塔（ユーザー）+ S 戦略チーム
> 目的: 「FX 戦略評価のための統計的フレームワーク（KPI 定義・検定・複数試行補正）を独立に設計・実装・検証する」ラボの全体方針

> **2026-08-29 起票**: `minmax-fx-day-trading-lab`（親 PJ）の評価フレームワーク部分を分離・独立 PJ 化。親 PJ の戦略試行サイクルを止めずに、評価装置の改善を独立に進める。

## 1. ゴール（北極星）

**「Bailey & Lopez de Prado (2014) 等の業界標準に整合した、選択バイアスを必須補正する FX 戦略評価フレームワークを v0.2 として設計・実装し、親 PJ へ stable なマージ提案を出すこと」**

補助指標:
- K4m 閾値 1.5 → 1.2 への緩和（市場構造との整合）
- min_n_trades=300 → 50 hard floor + DSR 動的補正
- DSR ≥ 0.95 を必須 KPI として追加
- permutation test の block 版デフォルト化
- 親 PJ 過去 11 戦略の DSR 遡及計算

## 2. スコープ

### In Scope
- KPI 閾値の導出と正当化
- 統計検定の手法選定と実装（permutation, DSR, block bootstrap, Bonferroni/Holm）
- 複数試行補正（Deflated Sharpe Ratio, PBO via CSCV）
- 親 PJ の戦略に対する遡及的評価
- フレームワークの比較検証（v0.1 vs v0.2）

### Out of Scope
- 新しい取引戦略の考案（親 PJ のスコープ）
- バックテストエンジンの実装（親 PJ の `simulator.py` を流用）
- ブローカー API 接続（親 PJ の `gmo_fx_client.py` を流用）
- フォワードテストの実行（親 PJ 側で実行・本 PJ では評価のみ）

## 3. 親 PJ との関係

```
minmax-trading-pilot        (FX 自動売買の親 PJ)
  └── minmax-fx-day-trading-lab   (FX バックテスト・戦略検証)
        ├── 戦略実装
        ├── バックテストエンジン
        ├── 評価フレームワーク ← 【本 PJ】minmax-fx-eval-framework に分離
        └── フォワードテスト
```

本 PJ の成果物が stable になった時点で親 PJ へマージ:
1. 親 PJ の `src/minmax_fx_dt/decision/criteria.py` を本 PJ の実装で置換
2. 親 PJ の `src/minmax_fx_dt/backtest/permutation.py` を本 PJ の実装で置換
3. 親 PJ の過去 11 戦略判定を新フレームワークで遡及再評価
4. 親 PJ の `portfolio-ledger.md` に DSR 列を追加

## 4. 検証プロセス（4 フェーズ）

### Phase 1: フレームワーク設計
- `research/フレームワーク再設計/00-spec.md` で KPI 閾値・検定手法を**結果を見る前に**数値固定
- v0.2 推奨案（A2+B2+C3+D1）の司令塔承認

### Phase 2: フレームワーク実装
- `src/minmax_fx_eval/statistics/dsr.py` の DSR 実装
- `src/minmax_fx_eval/statistics/permutation.py` の block デフォルト化
- `src/minmax_fx_eval/decision/criteria.py` の v0.2 適用
- `tests/` の回帰テスト

### Phase 3: 過去判定遡及
- 親 PJ の 11 戦略に対して DSR を計算
- `research/フレームワーク再設計/03-過去判定遡及/` に保存
- 判定結果は原則変えない方針（DSR 値のみ追記）

### Phase 4: 親 PJ へのマージ提案
- 段階的導入（まず DSR を参考値として追加 → 後に必須化）
- 親 PJ の CI で回帰テスト green 化
- `portfolio-ledger.md` の更新

## 5. リスク・制約

- **C 査読の独立性**: Mavis 環境では物理的に単一 LLM のため、独立 adversarial review は擬似的にしか確保できない
- **DSR の N (試行数) の数え方**: 「保存された spec 改訂の数」と「実際に試したパラメータ組み合わせ」の解釈で N=19〜28 が変動
- **親 PJ へのマージ時の互換性**: 既存の 25 テスト + 本 PJ の 6 テスト = 31 テストの同時 green 化が必要
- **min_n_trades=50 hard floor**: サンプル 0 でも「有意」と判定されるリスクへの安全弁（DSR 計算不能時のフォールバック）

## 6. 完了条件

- (A) v0.2 フレームワークが実装され、テスト green
- (B) 親 PJ 過去 11 戦略の DSR 遡及計算が完了し、80% 以上の戦略で判定が維持される
- (C) 親 PJ へのマージ提案が司令塔に承認される
